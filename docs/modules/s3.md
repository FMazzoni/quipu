The ledger is a set of immutable objects in a bucket, not a git branch. Three
operations reach it — PUT, GET and ListObjectsV2 — and there is no DELETE,
because a batch is named after the store that wrote it and the event range it
closes over, so nothing quipu does can make one wrong afterwards.

## Why the transport changed

A git fetch takes a branch whole; there is no way to ask for part of one. So
every project's store carried every other project's ledger, and total local
storage grew as the square of the number of projects. Partial clone was measured
against a real daemon and the filter was ignored; sparse checkout only hides
objects a pack still holds; `git archive --remote` is commonly disabled. The
behaviour is not configurable away.

A GET names one prefix. That is the whole fix, and it is why the key layout puts
the project first:

```text
<url prefix>/<project key>/<store uuid>/<store uuid>-<lo>-<hi>.jsonl
```

A store LISTs `<project key>/` and reads its own project and nothing else. A
project nobody has touched in a year costs nothing. Put the store uuid first
instead and every machine would have to enumerate the whole bucket to find its
own project again, which is the shape this replaced.

## Credentials

`AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, plus `AWS_SESSION_TOKEN` when
the credentials are temporary. Standard names on purpose: a machine that can
already reach an object store has them set, and a quipu-specific spelling would
be a second thing to get wrong. Quipu never writes a credential to disk and has
no config file for one. When they are absent the error names the variables it
looked for, because the usual cause is that they were exported into a different
shell.

The url carries no region — `s3://<host>/<bucket>` names the endpoint outright.
SigV4 still needs a region in the credential scope, so `AWS_REGION` (or
`AWS_DEFAULT_REGION`) is used when set and `us-east-1` otherwise.

## Failure causes are kept apart

`Fault` has a variant per cause rather than one "request failed", and that is
load-bearing rather than cosmetic. Credentials absent and credentials rejected
want opposite fixes. A missing bucket and a key outside your policy both arrive
as a 403. A TLS trust failure and an unreachable host look identical from a
failed request. And SigV4's answer to a clock twenty minutes out is an opaque
signature error that sends people to rotate keys that were never wrong — so
`RequestTimeTooSkewed`, and an `AccessDenied` whose message talks about time,
become `ClockSkew` rather than "denied".

## HTTPS is not negotiable off

`s3://` implies https and there is no plaintext url form. The one exception is a
test-harness variable, `QUIPU_S3_PLAINTEXT`, which exists because the hermetic
end-to-end test is a `std::net::TcpListener` stub and a stub cannot terminate TLS
without dragging a TLS server and a certificate into the test tree.

**Setting it is not sufficient.** The endpoint host must also be a loopback
literal — `127.0.0.0/8`, `::1`, or `localhost` — and both conditions are required
before a single byte goes out in the clear. A variable alone would be a switch
that travels: exported once in a shell profile, or inherited by an agent, it
would quietly downgrade every request to every endpoint thereafter. Because quipu
presigns, the signature rides in the query string, so one cleartext request hands
anyone on the path a url they can replay for the whole signature lifetime with
the key's full rights. That is credential disclosure, not a weaker cipher.

Loopback is the boundary rather than operator discipline because it is the one
condition under which "an eavesdropper on the path" is not a coherent threat: the
packets never leave the machine. The decision is made from the host as WRITTEN and
never resolved — a name that resolves to loopback today is a lever someone else
can move tomorrow, and DNS is not an authorisation mechanism.

The practical consequence: an object store served over plain http cannot be used
as a ledger. Terminate TLS at the endpoint, or forward a local port to it and
point quipu at `localhost` — a tunnel is loopback, and the gate permits it.

## Signing

Requests are presigned urls, not `Authorization` headers: `rusty-s3` is a
sans-I/O signer that hands back a url, and `ureq` then makes an ordinary
request. There is therefore no auth header to inspect — the credential scope,
the signed headers and the signature all ride in the query string, which is what
the tests assert against.

`sign` is a free function rather than a method so the published AWS vectors can
be pinned against the exact call the client makes. A test that signs its own
request cannot see a wrong region, a wrong url style, or a swapped key and
secret; one that goes through `sign` can.
